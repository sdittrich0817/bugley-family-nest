# Studio makers and books
- Auth email branding uses the managed six-type handler; welcome sends after first verified, consent-gated setup with an event-derived idempotency key, never on later login. Failures do not block setup; /lovable/* routes verify their own callers. Why: branded delivery without email queues or changing family access.
- Start middleware configuration filters are browser-safe; request reads stay inside server middleware bodies, and CSRF applies only to server functions. Why: avoid client-bundle server imports while signed email routes keep their own verification.

- Trusted devices authorize only explicitly kid-facing handlers through `requireKidOrParentAuth`, with server-verified selected child, family ownership, revocation and daily-time checks; parent handlers retain managed authentication plus `requireParentDevice`. Why: opaque device cookies cannot become adult accounts or bypass child limits.
- Pairing and device credentials are hashed server-side, raw device secrets are HttpOnly cookies, and parent PIN only opens navigation to normal parent sign-in. Why: installation never persists a parent password or grants adult authority from a four-digit PIN.
- Offline installation uses one preview-safe PWA wrapper and generated worker caching only public assets and the static offline screen. Why: private data and authentication never become offline caches.

- My Cast characters are `studio_creations` rows of kind `character`; their stored portrait is the reference image for later pictures. Why: reuse album save/delete/restore rules.
- Story creations retain ordered child-authored pages and map; server-only updates use optimistic version checks and coaching loads saved content. Why: family isolation and exact authorship survive workspace changes.
- Comic Maker uses the shared StorySetup and BugleyStep flow, server-created age-band panels, hidden scene planning and saved one-time follow-ups; comicCells defines automatic page geometry including the wide big moment for screen and print. Image vision supplies speech placement, and dialogue/layer actions never generate or charge glow; askBugley reads comicId/panelId and the book Bible. Why: child authorship and simple screens with consistent art, private storage and text separate from images.
- Books are `studio_creations` of kind `book` whose details hold format, locked style/cast, Story Bible, ordered chapterIds, author/pen-name status, dedication and cover; chapters are ordinary story/comic creations with `bookId` and shared `project`. Bible updates come only from children's saved chapters via `absorbAndRecap`, and story/comic coaching reads the bible. Print-minimum rules live in `src/lib/book.ts`. Why: reuse maker lifecycles and album projects while one source keeps the whole book consistent.
- Arcade games (`games.ts` rules, `games.functions.ts`) serve only pre-made `game_content` rows edited in /admin; answers stay server-side, rounds are graded and rewarded (sparks, levels, game badges, capped bonus glow via giftGlowServer) only in server functions, and no AI runs during play. Why: kids can't cheat rewards and nothing unchecked is generated mid-game.
- PLAY launch games use parent-scoped `play_sessions` with bounded server-graded turns and optimistic move claims; finish_play_session locks child/session and atomically awards stars, badges and capped local-day glow. Shared stickers contain only checked object concepts and safe artwork through images.server; Bugdex stores private child-to-sticker keys. Doodle requests accept bounded strokes only, re-render server-side and safety-check before guessing. Why: no uploaded images, client scores, duplicate rewards or family text shared in the library.
- Game Builder games are `studio_creations` of kind `game` whose details are a validated game file (template + settings) read by fixed engines in `src/components/games/engines.tsx`; AI only fills settings from allow-listed values, art is library sprites or the child's own creations, and all game text is guarded on save. Why: kids design games without any generated code running.
- Printed books: kids only create `print_requests`; parents order through `print.functions.ts`, which re-quotes with Lulu server-side, records a `print_orders` row and charges via Stripe embedded checkout. The payments webhook marks it paid and `advanceOrder` (`print.server.ts`) builds PDFs (`print-pdf.server.ts`), runs Lulu validation and submits the job; Hub "Check status" re-runs it. Formats, markup and sandbox/live live in admin-edited tables. Why: no browser path can set prices or reach the printer, and each step is resumable.
- Every Studio image goes through `src/lib/images.server.ts` (guard, glow charge with refund, server-built prompt from admin style recipe + no-text suffix, admin-chosen Replicate model per mode, fail-closed AI image check, private `studio-images` storage). Character Lock: heroes store a reference set and fixed Character DNA (inserted verbatim into prompts); stories/comics/books lock style and snapshot the scene model on first use (`details.modelLock`, book-level for chapters); scenes with locked characters get a vision drift check with up to 2 free retries, logged to `drift_checks`. Max 3 locked characters per book. Why: one audited path and consistent characters even when admin defaults change.
- Studio creations are written only by server code; rename actions guard child text before an ownership-checked write, and only parent-mode sessions restore or purge within 30 days. The Studio never accepts uploads. Why: direct browser updates cannot bypass moderation or destroy work permanently.
- Character consistency and reference safety checks fail closed; immutable art snapshots include the model and style recipe, and portrait provenance is server-recorded. Why: outages, weak matches and changed defaults cannot silently deliver inconsistent art.
- Make a Picture uses server-enriched rendering instructions and a saved preview; upgrades atomically claim that owned preview, use its stored idea/style/hero and image reference, and replace the same album entry. Its distinct glow spend kind leaves other finished-image costs unchanged. Why: no client-controlled discount, duplicate upgrade or changed subject.
- Tell a Story uses StorySetup and BugleyStep with server-created age-band pages, saved follow-up markers, and hidden illustration planning from saved content; page edits preserve exact words and invalidate old art, and chapter conversion carries cover/model lock into the book. Why: one question per screen without losing authorship or Character Lock.
- Studio Create V3 starts with an approved new/saved character, then initializes a production-shaped output with server-validated count and character ownership/style; optional coaching never writes scene text. Draft character rows carry characterDraftV3 and are excluded from approved cast. Why: child-led creation and resume reuse the existing store without treating draft characters as approved references.
- V3 picture revisions pass only a server-verified saved art path into the audited image pipeline; generation claims the project and replacement occurs only after success, with refunds on failed saves. Why: targeted edits retain original art and cannot inject another family's image or double-write a scene.
- Full workspace snapshots live in service-role-only studio_project_history, recorded by an update trigger; restores append history and preserve art/book locks. Legacy studio_versions retains page undo. Why: metadata, cast, layers and content restore without deleting revisions.
- Glow spends accept an idempotency op key (glow_ops table) and failed generations refund through glow_refund (daily balance first, then bonus). Why: retries never double-charge and refunds restore the right balance.
- Bugley can offer actionable suggestion chips from the allow-list in src/lib/studio-actions.ts (bugleyActions intent map); the client only executes those exact ids. Why: suggestions do things without trusting model output.
- Workspace metadata lives within existing creation details and survives production parsers; drafts are production-shaped, and server actions validate attachments, reference style and owned preview provenance. Why: early resume reuses existing readers without creating a second project store.

- The child first-session welcome auto-opens only for children created after the stored `onboarding_settings.welcome_launched_at` who haven't skipped/finished it; records and events are written only by server functions after child verification, hold no child content, and never touch Glow or rewards. Welcome cards open only existing routes chosen per band in `onboarding.ts` (a game the arcade offers that band; Create's character-first start). Why: existing children aren't surprised, onboarding stays private and side-effect free, and no band is sent to a hidden game.
- Game finish-screen takeaways for welcome first games come from pure functions in `src/lib/takeaways.ts` fed only by round evidence (checked pairs/photos, caught mistakes); with no evidence they encourage rather than claim learning. Why: children are never told they taught or corrected the AI when they didn't.
- Parent Hub welcome status is derived by the pure `welcomeParentStatus` from the parent-RLS-readable welcome record and launch date (read with the parent session, never the admin client) and shows only outcome and date, never child content. Why: parents see what happened without new private data or privileged reads.
- V3 comic panel prompts come from `src/lib/comic-continuity.ts`: the child's exact scene/change words lead and are never cut (over-limit text is rejected), AI revision output is labelled notes only, and continuity uses only earlier drawn panels' child descriptions; first draws freeze the cast into versioned private snapshot copies (`details.castSnapshot`), with older comics falling back to live characters. Paint ops own claim/charge/save/refund: only the claiming op may save, refunds go through `glow_refund_op` (once per charged op, failures alert admins), and stale claims reset without touching art. Why: continuity and fidelity without new tables, double refunds or locked-out children.
- Temporary child-facing notices live in `service_notices` (anon reads only active rows) via `DrawingRestNotice`; disable by setting active=false, not by code edits. Why: outage messaging turns off instantly without a publish.
- Co-op demo requests insert server-side via `submitDemoRequest` with per-IP and per-email limits on the shared attempt counter; browsers have no direct insert grant. Why: spam cannot bypass the limits.
- `has_role`/`has_active_subscription` answer anon/authenticated callers only about themselves unless the caller is admin (`caller_may_inspect`); service_role and direct DB contexts are unrestricted. DB checks live in `tests/db/`. Why: no cross-account role/plan disclosure while every RLS `has_role(auth.uid(), …)` check keeps working.
- V3 comic Story Memory lives in `details.storyMemory` (pure rules in `src/lib/comic-memory.ts`): items are exact excerpts of one panel's child description, keyed to that description's stamp, grounded (negated/uncertain/unwritten-change items dropped) and used only for later drawn panels while the stamp still matches; notes are taken alongside the drawing and saved in the same write as the art, never blocking it. Every comic character is frozen before first use (`missingSnapshotIds`/`mergeSnapshots`); with any frozen copy present `resolveCast` refuses rather than falling back to live characters, before any charge. V3 covers (`prepareV3Cover`) decide one intended cast with `intendedCoverCast` (`src/lib/cover-cast.ts`): explicit child words that include or leave out characters win, while unclear or no cast words keep every frozen character; that one decision picks the references, the named cast after the child's words, the memory details, and exactly who the character check requires. Revision checks are report-only `drift_checks` rows with `attempt = 0` and no child text, excluded from drift rates. `comicSchema` must keep `castSnapshot` and `storyMemory` so comic edits never drop them. Why: long-comic continuity without new tables, invented facts, live-reference swaps or stale overwrites.
- V3 comic input: every comic box uses the shared VoiceButton (browser speech recognition only, one listener at a time, no audio kept; words land in the editable box and follow the normal guarded save); age-band setup defaults live in `comic-setup.ts` and only decide what shows first; character ideas save quietly through a one-at-a-time queue with server-assigned versions and a conditional write (compare-and-swap), so delayed or other-device saves and closed ideas never win and the child chooses when two screens disagree; every child microphone (VoiceButton and useVoiceInput) obeys the single CHILD_VOICE_ENABLED switch in `kid-input.ts`, and VOICE_IN_NEW_BOXES additionally gates boxes that had no microphone before A3.2; unpublished, fully drawn V3 comics grow only through editComic `extend` (2 or 4 panels on a new page, up to 12). Why: easier input for young children without new data paths, lost options or overwritten work.
- V3 comic panels and covers (paintV3Scene, editComic) draw only after `freezeComicCast`/`frozenCastProblem` confirm at least one approved character with valid family-owned frozen copies in the comic's look, and generateImage `frozenCast` refuses empty or live casts before charging; drawn V3 comics can't get an empty cast, and new comics start only character-first (older idea/title starts refuse new comics). Why: no comic art is drawn or charged without the frozen-character guarantee, while older comics keep working.
- A3.4.1 idea-first V3 comics (pure rules in `src/lib/comic-idea.ts`; Explorers/Builders only, refused server-side for other bands) are ordinary V3 comic rows created by `saveV3Idea` with a device-chosen id and the exact idea in `workspace.originalIdea`; `workspace.ideaStage` ("idea" → "cast") stays until `setV3IdeaPlan` confirms an owned, approved, single-look cast, and every comic drawing path refuses while it is set. Idea saves use server-assigned `ideaVersion` conditional writes, cast/plan uses the comic timestamp, and character drafts made inside it carry `forComic` (hidden from in-progress lists, restored on reopen). The idea is never read by Story Memory, panel or cover prompts. Why: idea-first reuses character-first protections with no new tables, duplicate comics, stale overwrites or uncharacterised drawings.

- Spending gate: family-auth scopes downstream AI; synthetic scopes reject family entitlements and use separate budgets. `aiObject` uses the Gateway SDK, terminal/refusal checks and bounded output; image cost preflight embeds the exact full-resolution bytes priced by Astra's patch rules. Drawing prices reject unknown models/settings/versions; candidates and transport retries reserve before Glow. Unknowns keep holds pending service-only admin-attributed reconciliation. Why: no unchecked output, mutable-image cost race or guessed-price fallback.
- Price reviews expire after 30 days; synthetic benchmark runs require fresh pinned-version/rate evidence, immutable hashed adult references and the whole isolated batch reservation. Shared image-check contracts preserve production checks; the runner has no public entry point or automatic/live adapter. Why: bounded preparation cannot silently initiate paid work or drift safety rules.
